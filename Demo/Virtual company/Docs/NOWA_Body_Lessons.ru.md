# Слой тела — уроки, записанные под ситуацию

English: [NOWA_Body_Lessons.en.md](NOWA_Body_Lessons.en.md)

Модули (`Demo/Virtual company/src/nowa_body/`): `feedback_loop.py`, `runtime.py` (`BusinessAgentRuntime`, подкласс runtime платформы), `strict_binder.py`, `business_event_encoder.py`. Только stdlib.
Связано: #18 (квантование отзыва), [Docs/architecture/two-tier-plasticity.ru.md](../../../Docs/architecture/two-tier-plasticity.ru.md).

Ядро не меняется: ни когнитивные модули, ни слой тела платформы `src/mcp_body/`. Сотрудник расширяет классы платформы (`BusinessAgentRuntime`, `SchemaBinder`, `GenericEncoder`, `ProposedAction`) в демо. Механизмы ниже не зависят от домена; нужен ли какой-то из них в `mcp_body`, решает мейнтейнер.

## 1. Проблема

Недели работы агента на слое тела (закупщик Virtual company в своём симуляторе) показали, что тело не передавало уму ситуацию, к которой относится исход:

1. Отзыв об одобрении сохранялся без контекста, в котором принято решение, поэтому урок нельзя было вспомнить в той же ситуации.
2. Отклонённый вызов сохранялся как «этот инструмент, награда отрицательная». Гиппокамп тянет к действию из вспомненного эпизода независимо от знака, поэтому отказ всё равно тянул вызвать инструмент.
3. Вызовы, которые шлюз исполнил сам (никто не решал), сохранялись как полноценные одобрения.
4. Не было способа записать урок не о последнем шаге (поздний вердикт, поправка наставника). `apply_feedback_to_last_experience` берёт только последний шаг и квантует оценку (#18).
5. Если роль указала, откуда брать параметр, а в мире там пусто, привязчик угадывал в другом месте и строил вызов не к той сущности.
6. Общие токены `tool:/status:/field:/entity:` заполняли каждый контекст, и урок, записанный именованными событиями, совпадал с живым контекстом лишь частично.

## 2. Исходы под контекстом решения

- `ContextualProposedAction` (`ProposedAction` с `context_events`): runtime копирует в предложение токены контекста, на которых решал ум.
- `apply_feedback_to_agent(agent, record, encoder)`:

| Запись | Что сохраняется |
| --- | --- |
| Одобрено / изменено человеком | `store_lesson(контекст + токены исхода, tool_id, награда)` (`1.0` / `0.4`) |
| Отклонено | `store_lesson(контекст, wait_and_monitor, 1.0, consequence="call_rejected")` — «здесь ждать»; `record_action_outcome(tool_id, -1.0)` обновляет счётчики выбора |
| Исполнено самим шлюзом (`decided_by` начинается с `system:`) | Слабый эпизод: награда `0`, интенсивность `UNJUDGED_INTENSITY = 0.1`, без метки исхода |
| Истекло | `store_lesson(контекст + токены исхода, tool_id, -0.2)` |

## 3. `store_lesson` и `BusinessAgentRuntime.teach`

`store_lesson(agent, context_events, action, reward, consequence)` сохраняет `контекст → действие → последствие` как эпизод гиппокампа (награда обрезается до `[-1, 1]`, интенсивность `|награда|`) и передаёт исход ядру через `Agent._record_known_outcome(context_events, action_id, outcome, episode, intensity)`, как это делает хост тамагочи. Это пишет лабильную метку на непрерывной награде и помечает эпизод для захвата в следующем сне; днём `stable_fingerprint` не меняется. Без двухуровневого ядра (заглушка) эпизод всё равно сохраняется.

`runtime.teach(context, action, reward, consequence)` — тот же путь, для собственных уроков тела (§4) и для хостов.

Непрерывная награда на этом пути обходит квантование в 5 уровней в `apply_feedback_to_last_experience` (#18); сам дефект ядра здесь не трогается.

## 4. Строгие `param_bindings`

```yaml
param_bindings:
  slot_id: {path: entities.items.0.id, strict: true}
```

Строгая привязка берёт значение только по своему пути. Если путь пуст, `StrictSchemaBinder.bind` возвращает `None` и пишет в `last_strict_miss` первый обязательный параметр, который не нашёлся. Тогда runtime пишет `teach(context, wait_and_monitor, STRICT_MISS_LESSON_REWARD = 0.5, consequence="nothing_to_bind")` — мир сказал, что делать нечего — и возвращает `strict_miss` в результате такта. Нестрогие привязки сохраняют прежний запасной путь.

## 5. Сиды

Без изменений. Прежняя версия этого PR записывала сиды роли со стабильностью `1.0`, чтобы они пережили первый сон; это обходило консолидацию во сне (ревью #50). На двухуровневом ядре это не нужно. Матрица на 5 зёрнах (закупщик Virtual company, жёсткий мир, 30 смоделированных дней) даёт те же результаты с обычными сидами — проба на день 30 84 ± 2 против 83 ± 3, потеряно продаж 448 ± 92 против 452 ± 86, перерасход 0 — а первая ночь переносит их в кору (10–12 паттернов после дня 1 против 1–3 при стабильности `1.0`). Сиды остаются обычными эпизодами гиппокампа (уровень состояния); `HippocampusSeeder` не меняется.

## 6. `token_rules.generic_tokens`

`BusinessEventEncoder(token_rules={"generic_tokens": False})` оставляет только размеченные бизнес-события (`event:*`, валентность/возбуждение/теги из аффективной разметки) и убирает общие токены `tool:/status:/field:/entity:`. По умолчанию `True` — прежнее поведение, роль без классификатора событий по-прежнему работает.

## 7. Тесты

`Demo/Virtual company/tests/test_body_lessons.py` (строгий режим обучения, без домена): `store_lesson` записывает контекст, действие и последствие; пишет только лабильный уровень; непрерывная и обрезанная награда; заглушка агента; без памяти → `None`; `teach` — тот же путь. Одобрение под контекстом решения; отказ — урок «ждать» с `call_rejected`; исполнение без решения слабое и без метки. Строгая привязка не угадывает, нестрогая угадывает, строгая читает свой путь; runtime пишет «ждать было правильно» при промахе строгой привязки. Общие токены по умолчанию есть, выключенные оставляют только именованные события.

## 8. Вне объёма

- Квантование в `apply_feedback_to_last_experience` (#18) в ядре.
- Любые изменения `mcp_body` платформы.
- Доменная конфигурация (какие события, привязки и сиды у роли) — конфиг роли, тестируется в демо.
