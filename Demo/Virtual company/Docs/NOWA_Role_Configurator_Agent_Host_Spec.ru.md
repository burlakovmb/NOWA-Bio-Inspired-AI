## Аннотация

English version: [NOWA_Role_Configurator_Agent_Host_Spec.en.md](NOWA_Role_Configurator_Agent_Host_Spec.en.md)

Спецификация хозяина сотрудников вводит слой рядом с конфигуратором ролей и разводит три сущности. Роль — данные работы в `nowa_roles/<role_id>/config.yaml`: серверы, органы, риск, затравка и аффективная карта; роль не запускается. Сотрудник — именованный экземпляр разума: файл `nowa_employees/<agent_id>/employee.yaml`, список идентификаторов ролей, собственный ритм и жизненный цикл; техническое поле ядра остаётся `agent_id` по шаблону строчной латинской метки длиной до 48 знаков. Сессия — живой runtime в памяти процесса, пока графический хозяин работает; на остановке разум пишется на диск. Два сотрудника с одной ролью имеют два гиппокампа, два вектора A(t) и две очереди одобрения. Сухой прогон роли и отдельное лабораторное окно сотрудником не являются: лаборатория знает четыре зашитых инструмента макета, тогда как у роли закупок уже описан живой HTTP-сервер `drivemcp` по адресу `http://localhost/DriveDemo/hs/mcp`, в который исполнение записи и опрос сенсоров из конфигуратора ещё не направляются.

Параметры записи собирает `SchemaBinder`. Каналы решения — идентификаторы инструментов записи и `wait_and_monitor`. Разум протокол не импортирует. Сон есть фаза консолидации `sleep_cycle` и задаётся в стенных секундах отдельно от интервала тика; пример карточки — тик 1 с, сон не чаще чем раз в 3600 с, циркадное окно часов 2–5 и порог усталости 0,85. Сон не следует из факта тика. Состав ролей меняется только в состоянии `stopped`; правка YAML роли во время работы оставляет сессии снимок момента старта и помечает плашку устаревших ролей. Затравка выполняется только при пустой памяти и не повторяется после остановки и повторного старта. Недоступный живой транспорт на старте переводит сотрудника в `error` и макетом не подменяется. Опрос касается только органов с `poll: true`; запись таким флагом быть не может. Одобрение видно в карточке и счётчиком ожидающих в списке. Состояния бейджа — остановлен, запускается, работает, спит, ждёт одобрения, останавливается и ошибка; ожидание одобрения тики не останавливает.

Ограничения H1–H17 включают единственную точку записи через `ApprovalGate`, запрет автоисполнения высокой и необратимой записи, `decision_only=True` на бодрствующем тике, запрет импорта `nowa_sandbox`, запрет добавлять оси аффективного пространства и требование успешной записи `mind.pkl` для нормальной остановки. Несколько ролей одного сотрудника складываются объединением органов с ключом `tool_id`; тот же ключ при разном уровне риска есть ошибка конфигурации, а одно имя инструмента на разных серверах даёт два органа. Приёмка версии хозяина выполняется на макете: старт, тики, остановка, восстановление числа эпизодов и независимость периода сна от числа тиков, в том числе при тике 60 с и минимальном интервале сна 3600 с. Живой прогон Drive отнесён к следующему ручному шагу и в автоматические тесты этой поставки не входит. Лимита на число сотрудников и на число одновременно работающих сессий нет.

# NOWA Role Configurator — Хост сотрудников (роли → экземпляр → start/stop)

**Версия:** 1.0  
**Статус:** готово к реализации — открытых вопросов нет  
**Дата:** 2026-08-27  
**Целевой пользователь:** тот же, что у конфигуратора ролей — настраивает
органы и интуицию без Python, затем запускает конкретного сотрудника.
**Конечная цель этой линии:** суверенный NOWA-сотрудник, который читает и
меняет данные в информационных базах через MCP-тулы (в т.ч. публикация 1С /
Drive / любой другой `MCPTransport`). Хост не знает, что такое «база» — он
знает органы.

**Родительские документы (не переписывать, только согласовать):**

- `NOWA_Role_Configurator_GUI_Spec.md` — GUI ролей, инварианты G1–G7
- `NOWA_Body_Layer_RoleConfig_Spec.md` — YAML роли как данные
- `NOWA_Body_Layer_AffectiveSpace_Body_Addendum.md` — SchemaBinder, не MotorAdapter
- `Docs/spec_affective_space_platform_body.md` — P1–P11, тул = орган
- `NOWA_Body_Layer_Phase1_AsBuilt_MCP_API.md` — `tool_id`, envelope, ApprovalGate
- `NOWA_Virtual_Employees_Architecture_Spec.md` — сотрудник = суверенная единица
- `src/storage.py` — `AgentStorage.save_agent` / `load_agent` (чекпоинт разума)

**Принцип этой спецификации:** конфигуратор ролей остаётся тонким визуальным слоем
над `role_config.py`. Хост сотрудников — *новый* слой рядом, не внутри
валидации роли. Роль описывает работу. Сотрудник — экземпляр разума, которому
эту работу выдали. Start/stop не редактирует YAML роли.

Имя в UI и в этой спецификации: **сотрудник**. Технический идентификатор
остаётся `agent_id` (так называется поле у ядра NOWA). Файл сущности —
`employee.yaml`.

## 0. Зачем это, если уже есть Dry Run и Body Lab

Сейчас в конфигураторе есть два разных «прогона», и ни один не является
сотрудником:

| Что есть | Что это на самом деле |
|---|---|
| Вкладка «Тестовый прогон» | Одноразовый `BodyLabSession` по *одной* роли, MockMCP, четыре зашитых тула (`get_stock_levels` / `get_suppliers` / `get_budget` / `create_purchase_order`), симулированные часы, `force_action` |
| Body Lab GUI (`run_body_gui.bat`) | Та же лаборатория, отдельное окно, сценарии склада |

Чего нет:

- сущности «этот сотрудник» с именем, памятью и назначенными ролями;
- назначения **нескольких** ролей одному разуму;
- длительного цикла start → тики по живым MCP → stop с сохранением разума;
- **своего** интервала тика и **своего** интервала сна у каждого сотрудника;
- опроса тех READ, которые эксперт пометил галочкой `poll` (лаборатория
  знает только четыре mock-тула `1c_erp`);
- очереди approval в том же окне, где нажали Старт.

Роль `procurement` уже содержит живой HTTP-сервер `drivemcp`
(`http://localhost/DriveDemo/hs/mcp`) и набор тулов к остаткам / поставщикам /
бюджету / заказу — Discover ходит в него. Исполнение WRITE и опрос сенсоров
из конфигуратора в этот сервер **не** идут. Разрыв именно здесь: органы
прописаны, тела-хозяина нет.

```
Роль (YAML)          Сотрудник (этот документ)        Мир
────────────         ─────────────────────────        ───
mcp_servers    →     составной реестр органов    →    MCPTransport.call_tool
mcp_capabilities     BusinessAgentRuntime.tick        (mock | http | sse)
seed / affect        hippocampus + A(t) + чекпоинт
                     ApprovalGate                     человек в GUI
```

## 1. Разделение сущностей (не смешивать)

| Сущность | Что это | Где живёт | Можно ли «запустить» |
|---|---|---|---|
| **Роль** | Описание работы: серверы, органы, риск, seed, аффект | `nowa_roles/<role_id>/config.yaml` | Нет. Роль — справочник |
| **Сотрудник** | Именованный экземпляр NOWA + список `role_id` + ритм (тик/сон) + жизненный цикл | `nowa_employees/<agent_id>/employee.yaml` + чекпоинт разума | Да: start / stop |
| **Сессия** | Живой runtime: разум + транспорты + очередь approval + поток тиков | в памяти хоста, пока процесс GUI жив; разум на Stop пишется на диск | Это и есть «запущен» |

Инварианты из архитектуры виртуальных сотрудников остаются в силе:

1. Сотрудник — суверенная единица. Реестр тулов **per-employee**. Два
   сотрудника с одной ролью — два гиппокампа, два A(t), две очереди approval.
2. Обучение только во сне (`sleep_cycle`). Сон **не** следует из факта тика;
   его период задаётся отдельно и считается в **стенных секундах**, не в
   числе тиков (раздел 5.6).
   С #13: дневные исходы идут в лабильный слой, стабильные значения меняются только в `Agent.sleep()`; хост сотрудника передаёт `dt` ([issue-13-demo-virtual-company.ru.md](../../../Docs/specs/issue-13-demo-virtual-company.ru.md)).
3. Разум не импортирует MCP. Каналы BG = WRITE `tool_id` + `wait_and_monitor`.
4. HIGH_WRITE / IRREVERSIBLE не обходятся A(t) и не обходятся кнопкой Старт.
5. MotorAdapter **не** точка расширения. Параметры WRITE собирает
   `SchemaBinder`.

**Следствие для UI:** список сотрудников — соседняя секция главного экрана
конфигуратора, не восьмая вкладка редактора роли. Редактор роли не умеет
Старт. Карточка сотрудника не умеет править `config.yaml` роли.

## 2. Информационная архитектура GUI

Конфигуратор запускается тем же `run_role_configurator.bat`. Главный экран
становится двухсекционным (роли слева, как сейчас; сотрудники справа).

```
┌─────────────────────────────────────────────────────────────────┐
│  NOWA Role Configurator                          [EN] [RU]      │
├──────────────────────────────┬──────────────────────────────────┤
│  Роли компании               │  Сотрудники                       │
│                              │                                   │
│  📦 Менеджер по закупкам  ✓  │  👤 Закупщик А     ● stopped     │
│     procurement · 8 тулов    │     роли: procurement             │
│                              │     тик 1с · сон ≥ 1ч             │
│  [+ Новая роль]  [Открыть]   │     [Старт]  [Открыть]            │
│                              │                                   │
│                              │  👤 Операционист   ● running     │
│                              │     роли: procurement, sales      │
│                              │     тик 60с · pending: 1          │
│                              │     [Стоп] [Открыть]              │
│                              │                                   │
│                              │  [+ Новый сотрудник]              │
└──────────────────────────────┴──────────────────────────────────┘
```

Статусы сотрудника (ровно эти строки, без свободного текста в бейдже):

| Код | UI | Смысл |
|---|---|---|
| `stopped` | остановлен | нет сессии; разум на диске, если уже работал |
| `starting` | запускается | соединяемся с MCP, восстанавливаем или сидим память |
| `running` | работает | поток тиков идёт |
| `sleeping` | спит | идёт `sleep_cycle` (сессия жива, это не Stop) |
| `awaiting_approval` | ждёт одобрения | есть PENDING; тики **продолжаются**, WRITE этого action_id не уходит |
| `stopping` | останавливается | доиграть тик, записать чекпоинт, закрыть транспорты |
| `error` | ошибка | сессия снята; чекпоинт пишется, если разум успели собрать; текст в карточке |
| `stale_roles` | (плашка, не бейдж) | сессия `running`, YAML ролей изменился после Start — нужен рестарт |

Двойной клик / «Открыть» на сотруднике → **карточка сотрудника** (не редактор роли).

Лимита на число сотрудников и на число одновременно `running` **нет**.
Каждый `running` — свой поток, свой реестр, своя очередь approval.

### 2.1 Диалог «Новый сотрудник»

```
┌─────────────────────────────────────────────┐
│  Новый сотрудник                              │
│                                               │
│  Имя:  [Закупщик А                        ]   │
│  id:   [buyer_a]  (slug, уникален)            │
│                                               │
│  Роли (хотя бы одна, только ✓-валидные):      │
│  ☑ procurement — Менеджер по закупкам         │
│  ☐ sales — …                                  │
│                                               │
│  Ритм                                         │
│  Тик:     [1] секунд     (пример: 1 или 60)   │
│  Сон не чаще чем раз в: [3600] секунд         │
│                                               │
│         [Отмена]            [Создать]         │
```

- `agent_id`: `[a-z][a-z0-9_]{1,47}`, уникален в `nowa_employees/`.
- Невалидная роль (✗ `RoleConfigError`) в чекбоксе **задизейблена**.

- После создания файл пишется сразу. Чекпоинта разума ещё нет — первый

### 2.2 Карточка сотрудника

```
┌─────────────────────────────────────────────────────────────────┐
│  ← Сотрудники     Закупщик А                 [● running]        │
├─────────────────────────────────────────────────────────────────┤
│  Роли:  [procurement ×] [+ добавить роль]                        │
│          (состав ролей — только в stopped)                       │
│                                                                 │
│  Ритм:  тик [  1 ] с    опрос сенсоров [ 30 ] с                  │
│         сон не чаще [ 3600 ] с                                   │
│         окно сна (часы) [ 2 ]–[ 5 ]   порог усталости [ 0.85 ]   │
│         (тик/сон можно менять на лету; состав ролей — нет)       │
│                                                                 │
│  MCP: drivemcp  http  ok · 1c_erp  mock  ok                     │
│  Органы: 6 READ / 1 WRITE · last sensor 12s ago                 │
│  Память: checkpoint 14:02 · 128 эпизодов                         │
│                                                                 │
│  ⚠ Роли изменены после старта — рестартните сотрудника,          │
│    чтобы подхватить новый YAML.                    [Рестарт]     │
│                                                                 │
│  [▶ Старт]  [■ Стоп]     Стоп доступен всегда, включая error     │
│                                                                 │
│  Очередь одобрения                                              │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ mcp__drivemcp__create_purchase_order                      │  │
│  │ supplier_id=…  sku=…  qty=45                              │  │
│  │ [Одобрить] [Отклонить] [Править params]                   │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                 │
│  Журнал тиков (хвост)           Память (narrative, как dry-run) │
│  t=14 action=mcp__drivemcp__…   Когда низкий остаток → …        │
│  t=15 wait_and_monitor                                          │
└─────────────────────────────────────────────────────────────────┘
```

Правила UX:

- **Старт** недоступен, пока нет ни одной роли, пока статус не `stopped`/`error`,
  пока составной конфиг не проходит `validate_role_config` (раздел 4).
- **Стоп** — совместный признак остановки: флаг, доиграть текущий тик, **полный
  чекпоинт разума** (раздел 5.7), закрыть транспорты, статус `stopped`.
  Не `kill -9`.
- **Состав `role_ids`** меняется только в `stopped`. Это карточка сотрудника,
  не редактор роли.
- **Редактор роли** остаётся доступен, пока сотрудник `running`. Сессия
  держит состав, загруженный на Start. После сохранения YAML роли карточки
  затронутых `running`-сотрудников показывают плашку `stale_roles` и кнопку
  **Рестарт** (= Стоп с чекпоинтом + Старт с новым compose и **восстановленным**
  разумом). Пользователь решает, когда рестартовать; хост сам не перезапускает.
- Закрытие окна конфигуратора с живыми сотрудниками → диалог «остановить N
  сотрудников и сохранить память?» (по умолчанию Да). Каждый проходит тот же
  путь Stop, что и кнопка.

Dry-run на вкладке роли **не трогаем**. Это проверка конфига, не сотрудник.

### 2.3 Одобрение — только карточка (Q-H-4)

Человек одобряет WRITE **только** в карточке сотрудника: очередь, кнопки
Одобрить / Отклонить / Править params. В списке сотрудников допустим счётчик
`pending: N` — это приглашение открыть карточку, не отдельный канал решения.

Запрещено в v1: всплывающее уведомление, звук, модальное окно на тик. Конфигуратор не
перехватывает фокус, если открыт редактор роли. Пропущенное одобрение
остаётся в очереди, пока человек не зайдёт в карточку (или не остановит
сотрудника: PENDING уезжает в sidecar).

### 2.4 Вкладка «Инструменты» роли — галочка опроса (Q-H-9)

На карточке каждого тула, рядом с «включён в роль» и «нужно одобрение»,
появляется чекбокс **«Опрашивать как сенсор»** (`poll`). Это поле роли, не
сотрудника: какие органы хост дергает сам, решает эксперт роли.

| Тул | Чекбокс |
|---|---|
| READ_ONLY, включён в роль | доступен; пользователь ставит явно |
| WRITE (любой риск) | выключен и **disabled** — опрос мышцы запрещён |
| Не включён в роль | disabled; `poll` в YAML не пишется, пока тул не включили |

Значение по умолчанию при включении тула в роль и при Discover: **`poll: false`**.
Хост никогда не начинает бить в базу «потому что схема пустая» — только
галочка. Существующая роль `procurement` в рамках этой поставки получает
явные `poll: true` на тех READ, которые должны быть датчиками (остатки,
поставщики, бюджет, точка заказа, потребности) — миграция YAML, не эвристика
рантайма.

Если `poll: true`, а в `input_schema` есть `required`, которых нечем
заполнить: хост этот тик тул **не** зовёт, в журнал пишет предупреждение,
сессия не падает. На той же карточке тула тогда показываются поля
`poll_defaults` (по одному на каждый required). Пока defaults пусты и
WorldState не закрыл required — датчик молчит.

Фрагмент YAML роли:

```yaml
- tool_id: mcp__drivemcp__get_stock_levels
  risk_level: read_only
  poll: true
  poll_defaults: {}          # не нужно: required нет

- tool_id: mcp__drivemcp__list_metadata_objects
  risk_level: read_only
  poll: true
  poll_defaults:
    metaType: Catalogs       # иначе хост не вызовет тул сам
```

## 3. Данные: `employee.yaml` и чекпоинт

Новый корень рядом с ролями, не внутри `nowa_roles/`:

```
Demo/Virtual company/src/nowa_employees/
  <agent_id>/
    employee.yaml
    .history/employee_<timestamp>.yaml
    mind.pkl                 # полный чекпоинт разума (раздел 5.7)
    session_sidecar.json     # WorldState, очередь approval, sleep-scheduler
```

Схема `employee.yaml` v1:

```yaml
schema_version: 1
agent_id: buyer_a
display_name: "Закупщик А"

# Порядок = порядок overlay классификаторов / merge aliases (раздел 4).
# Минимум один id.
role_ids:
  - procurement

# Ритм этого сотрудника, не свойства роли.
# Тик = как часто разум принимает решение (стенные секунды).
# У одного сотрудника 1, у другого 60 — оба валидны.
tick_interval_s: 1.0
sensor_refresh_interval_s: 30.0

# Сон считается в стенных секундах, не в числе тиков.
# min_interval_s — анти-thrash: сон не чаще чем раз в этот промежуток.
sleep:
  min_interval_s: 3600          # 1 час; при тике 1с это не «каждый тик»
  circadian_window: [2, 5]      # часы локальных суток; [0, 0] = выкл
  fatigue_threshold: 0.85       # Process S; null = не будить по усталости

seed_intuition: true            # только если память пуста (раздел 5.1)
auto_execute: false             # никогда не снимает HIGH_WRITE/IRREVERSIBLE

created_at: "2026-08-27T12:00:00"
updated_at: "2026-08-27T12:00:00"
```

`mcp_overrides` (своя база на ту же роль) в v1 **нет**. Учётка и URL живут
в YAML роли. Разные базы на одну роль — этап после v1, схема к этому готова
добавить список, хост пока не читает такого поля.

Валидация ритма при загрузке:

| Поле | Правило |
|---|---|
| `tick_interval_s` | `> 0`, разумный потолок 86400 (сутки). Иначе `EmployeeConfigError` |
| `sensor_refresh_interval_s` | `>= tick_interval_s` рекомендуется, не обязательно; `> 0` |
| `sleep.min_interval_s` | `>= 0`; `0` разрешён только как явный «лабораторный» режим и требует подтверждения в UI («сон сможет случиться на каждом тике») |
| `circadian_window` | два целых 0–23; `[0, 0]` или `start == end` = окно выключено (как as-built) |

Ограничения файла:

| # | Правило |
|---|---|
| **E1** | GUI не пишет `nowa_roles/**` при создании/старте сотрудника |
| **E2** | `role_ids` ссылаются на существующие `nowa_roles/<id>/config.yaml` |
| **E3** | Пустой `role_ids` — ошибка загрузки, не «сотрудник без органов» |
| **E4** | Чекпоинт (`mind.pkl`) принадлежит этому `agent_id`; чужой файл не подмешивается |

## 4. Слияние ролей → составной `RoleConfig`

Назначение нескольких ролей — это **union органов**, не «два мозга» и не
рантайм-переключение persona. Один `BusinessAgentRuntime`, один реестр,
один `WorldState`.

Орган идентифицируется **уже** как `tool_id = mcp__<server_id>__<tool_name>`.
Один и тот же человеческий тул на разных MCP — два разных органа
(`mcp__1c_erp__get_stock_levels` ≠ `mcp__drivemcp__get_stock_levels`).
Коллизия «два get_stock_levels» при слиянии ролей **не возникает**, пока
тулы привязаны к разным `server_id`. Это закрывает Q-H-1.

Истинный дубль — две роли включили **один и тот же** `(server_id, tool_name)`.
Это один орган, не конфликт имён: записи сливаются в один экземпляр.

Новый модуль (логика не в GUI): `nowa_body/role_compose.py`.

```text
compose_roles(role_ids, roles_root) -> RoleConfig
```

Каждый id загружается через `load_role_config` (G1 жив). Затем слияние.

| Поле | Правило |
|---|---|
| `role_id` | составной: `"+"`.join(role_ids) — метка, не путь на диске |
| `display_name` | `" + ".join(display_name каждой роли)` |
| `mcp_capabilities` | ключ = `tool_id` (= сервер + имя тула). Первый раз — берём. Повтор того же `tool_id`: если capability **эквивалентна** (risk, schema, approval, tags, **`poll`**, `poll_defaults`) — один экземпляр; если поля расходятся — `RoleConfigError` с указанием обеих ролей и `tool_id` |
| `mcp_servers` | ключ = `server_id`. Повтор: тот же транспорт/url/username — один сервер. Расхождение url/transport/username → ошибка (это уже не «тот же MCP»). Password: непустой побеждает пустой; оба непустые и разные → ошибка |
| `affective_mapping` | union по имени события. Одинаковое имя, разные valence/arousal/tags → ошибка |
| `seed_corpus` | конкатенация в порядке `role_ids`, затем `validate_role_config` |
| `param_bindings` / `field_aliases` | merge ключей; повтор ключа → значение **более поздней** роли + `warnings.warn` |
| `event_classifier` | все заданные callable как overlay, порядок = `role_ids`. Нет ни одного — ок |
| `motor_adapter` | **игнорируется** |

После слияния — тот же `validate_role_config`. Невалидный состав → Старт
запрещён.

Поле `poll` / `poll_defaults` парсится в `role_config._parse_capability` и
живёт на `MCPCapability` (новые поля, дефолт `poll=False`,
`poll_defaults={}`). GUI не конструирует capability в обход загрузчика (G1).
`poll: true` на WRITE при загрузке → `RoleConfigError` (нельзя обойти UI).

## 5. Хост: `EmployeeSession` (не `BodyLabSession`)

Лаборатория остаётся для dry-run и Body Lab. Живой сотрудник — новый класс.

Предлагаемые модули:

```
nowa_body/
  employee_config.py          # load/save employee.yaml
  role_compose.py             # compose_roles()
  mcp_router.py               # server_id → MCPTransport
  sensor_poller.py            # какие READ звать и с какими args
  employee_checkpoint.py      # mind.pkl + sidecar через AgentStorage
  employee_session.py         # runtime + cooperative loop
  gui_configurator.py         # секция сотрудников (view)
  gui_employee_controller.py
```

`nowa_sandbox` не импортируется.

`SleepScheduler` as-built считает анти-thrash в **тиках**
(`min_ticks_between_sleep`). Для сотрудников с разным `tick_interval_s` это
ломает смысл («3600 тиков» при тике 1 с = час, при тике 60 с = 60 часов).
Хост обязан кормить планировщик **стенным временем**: либо расширить
`SleepScheduler` полем `min_interval_s` и сравнивать elapsed seconds, либо
обёртка, которая переводит `min_interval_s / tick_interval_s` только как
fallback. Канон спецификации — **стенные секунды** (раздел 5.6). Лаборатория
и её тесты не обязаны меняться в этой поставке.

### 5.1 Сборка сессии при Start

1. Прочитать `employee.yaml`.
2. `compose_roles(role_ids)` — снимок на момент Start. Дальнейшие правки
   YAML ролей эту сессию не меняют, пока пользователь не нажмёт Рестарт.
3. Построить `MCPToolRegistry(agent_id)` (`build_tool_registry`).
4. Для каждого **enabled** сервера открыть транспорт:
   - `mock` → `MockMCPClient` с каталогом роли (как Discover), не четыре
     зашитых тула лаборатории;
   - `http` / `sse` → `mcp_transport_from_server`;
   - `stdio` → отказ с понятной ошибкой.
5. Пинг: `list_tools()` на каждом живом транспорте. Недоступный HTTP →
   `error`, Старт неуспешен, **нет** тихого отката на mock.
6. Создать скелет разума: `AgentFactory.spawn_default(agent_id=...)` если
   ядро доступно, иначе fallback как `create_lab_agent`. Без `force_action`.
7. Память:
   - если чекпоинт есть и память **не пуста** → `load_agent` в этот скелет,
     seed **не** вызывать;
   - если чекпоинта нет **или** память пуста (нет эпизодов гиппокампа) →
     при `seed_intuition: true` вызвать `build_seeder(composed).seed_agent`;
   - сломанный pickle → статус `error`, seed **не** подставлять молча
     (это уничтожило бы идентичность). В карточке действие «сбросить память»
     — явное, с подтверждением.
8. `BusinessAgentRuntime`: ApprovalGate, encoder, `param_bindings` /
   `field_aliases`, SleepScheduler из YAML сотрудника,
   `sensor_refresh_interval_s`, **`simulated_tick_seconds = tick_interval_s`**
   (Process S растёт от прожитого времени этого ритма, не от «1 тик = 1 с»
   для всех).
9. `auto_execute=true` снимает approval только у WRITE ниже HIGH_WRITE.
   HIGH_WRITE/IRREVERSIBLE → `HardConstraintViolation`, Старт отменяется.
10. Восстановить sidecar, если был: `WorldState`, PENDING очереди
    (ещё не исполненные WRITE), счётчики SleepScheduler.
11. Запустить worker (раздел 5.4).

«Память пуста» = нет `mind.pkl`, либо после load у гиппокампа 0 experiences.
Повторный Старт после Стоп всегда идёт по ветке восстановления, не по seed.

### 5.2 Маршрутизация вызова (`mcp_router`)

`tool_id` = `mcp__<server>__<name>` (`split_tool_id`). READ и WRITE идут в
транспорт этого `server_id`. Хост не ветвится на «Drive» / «1С».

Исполнитель WRITE — **только** `ApprovalGate.mcp_executor` (B5).

### 5.3 Опрос сенсоров

Хост **не** опрашивает «все READ». Сенсор = capability с `poll: true`
(и только READ_ONLY — это уже гарантирует загрузчик). Три зашитых тула
лаборатории не используются.

Порядок аргументов вызова, если `poll: true`:

| Условие | Поведение |
|---|---|
| `poll_defaults` заданы | вызвать с ними (SchemaBinder может дополнить, не затирая defaults) |
| `required` пуст | вызвать с `{}` |
| `required` непустой, `SchemaBinder` заполняет все required из `WorldState` | вызвать с этими params |
| иначе | этот цикл пропустить, warning в журнале сотрудника |

Интервал опроса — `sensor_refresh_interval_s` сотрудника, не частота тика.
Контракт `BusinessAgentRuntime.tick` уже такой.

Observations:

```python
{
  "agent_id": employee.agent_id,
  "tool_results": { tool_id: envelope, ... },
}
```

Без доменных ключей `stock` / `suppliers` / `budget`. Ошибка одного READ →
envelope `{status: "error", ...}`, остальные сенсоры цикла опрашиваются.
Мёртвый транспорт на старте — шаг 5 раздела 5.1.

### 5.4 Цикл жизни потока

v1: **один daemon-поток на сотрудника** внутри процесса Tk. Лимита N нет.
Почему не subprocess: очередь approval и журнал в том же окне без RPC.

```
while not stop_flag:
    result = runtime.tick(sensor_fetcher, now=datetime.now())
    enqueue UI snapshot (простые dict)
    sleep(current_tick_interval_s)   # читается из employee.yaml / карточки
```

Tk из worker не вызывается. Карточка читает очередь через `after(200 ms)`.

Смена `tick_interval_s` / `sleep.min_interval_s` на карточке **на лету**:
следующий `sleep()` цикла и следующий `should_sleep` берут новые значения.
Смена `role_ids` на лету запрещена (только stopped). Смена YAML роли —
плашка, нужен Рестарт.

Stop:

1. UI ставит `stop_flag`.
2. Worker выходит после текущего `tick` / `call_tool` (v1 ждёт timeout
   транспорта, по умолчанию 30 с).
3. Полный чекпоинт (раздел 5.7). Если писать не удалось — статус `error`,
   сессия всё равно снимается, в карточке текст ошибки сохранения.
4. Закрыть HTTP-сессии, если клиент умеет.
5. Статус `stopped`.

Два сотрудника могут ходить в один MCP URL: транспорт шарить можно, реестр
и чекпоинт — нет.

### 5.5 Approval во время running

- PENDING WRITE: статус `awaiting_approval`, если очередь непуста; тики идут.
- Решение — **только** карточка сотрудника (`complete_approval` из UI-потока).
  Список показывает `pending: N`. Нет всплывающего уведомления, звука, модалки.
- Правка params — `modified_params` как в `ApprovalGate.decide`.
- На Stop очередь PENDING уходит в sidecar и возвращается на следующем Start
  (ещё не ушедший в мир WRITE не теряется).

### 5.6 Сон: не каждый тик, период свой

Сон — консолидация (`sleep_cycle`), не «пропуск тика». Вызывать его на
каждом `tick` нельзя: это и есть thrashing, о котором предупреждает
as-built `min_ticks_between_sleep`.

Проблема лаборатории, которую эта спецификация чинит для сотрудников:

- планировщик historically считает паузу в **тиках**;
- у сотрудников тик разный (1 с vs 60 с), поэтому «3600 тиков» — разное
  человеческое время;
- Process S (`update_waking`) уже умеет принимать `elapsed_seconds`.

Правила хоста:

1. `simulated_tick_seconds = tick_interval_s`. Час wall-clock бодрствования
   даёт один и тот же прирост Process S и 1-секундному, и 60-секундному
   сотруднику.
2. Анти-thrash — `sleep.min_interval_s` в **стенных секундах** с момента
   последнего `mark_slept`. Пока не прошло — `should_sleep` = false, даже
   если циркадное окно открыто и усталость высока.
3. Если пауза вышла: сон, когда (окно циркады открыто) **или** (Process S
   ≥ `fatigue_threshold`, если порог задан). Окно `[0,0]` / `start==end`
   выключает циркаду. `fatigue_threshold: null` выключает ветку усталости.
   Если обе ветки выключены, сотрудник не спит сам (только явная будущая
   кнопка «усыпить», не в v1).
4. Пока выполняется `sleep_cycle`, бейдж `sleeping`; это не Stop. Worker
   не стартует следующий тик, пока сон не вернётся.
5. Дефолт нового сотрудника: `min_interval_s: 3600`, окно `[2, 5]`, порог
   `0.85` — как канон лаборатории, но в секундах, не в тиках.
6. UI обязан показать, что сон и тик — разные ручки. Подсказка: «Тик — как
   часто сотрудник смотрит на мир. Сон — как часто он закрепляет опыт.
   Сон раз в тик сломает обучение.»

### 5.7 Чекпоинт разума (Stop → диск → Start)

Забывать сотрудника нельзя. Стоп фиксирует состояние **на момент стопа**;
следующий Старт поднимает того же.

Состав чекпоинта:

| Файл | Содержимое |
|---|---|
| `mind.pkl` | Всё, что пишет `AgentStorage.save_agent` при переданном `agent=`: гиппокамп, кора, selector (+ metadata каналов), A(t), affect, sleep_manager, нейромодуляторы, value layer, conflict arbitration, wakefulness / Process S, прочие поля, которые storage уже сериализует |
| `session_sidecar.json` | `WorldState` (results/entities/scalars/stats), записи одобрения со статусом PENDING, прошедшее время `sleep.min_interval`, tick_index, timestamp стопа, hash/mtime ролей, с которыми сессия была собрана (для плашки stale) |

Порядок на Stop: сначала `mind.pkl` (атомарно: писать `mind.pkl.tmp` +
replace), потом sidecar. Чтение на Start: mind, затем sidecar; битый sidecar
не отменяет восстановленный разум (очередь approval тогда пуста, WorldState
наберётся с первых READ).

Рестарт из-за смены ролей: Stop (чекпоинт) → compose нового YAML → Start с
тем же `mind.pkl`. Органы в selector после compose регистрируются заново
(`register_organs_on_agent`); старые каналы, которых больше нет в составе,
остаются в metadata selector, но не предлагаются runtime как мышцы.

Явного «сбросить память» в карточке (stopped): удаляет `mind.pkl` и sidecar
после подтверждения. Следующий Старт = пустая память → seed, если включён.

## 6. Связь с конечной целью (базы через MCP на платформе NOWA)

Платформенное тело уже умеет: Discover по HTTP, `tool_id` как канал,
`SchemaBinder`, ApprovalGate, envelope `status`. Хост этой спецификации —
длительный вызов того же контракта плюс ритм и память сотрудника.

Новая база = новый `mcp_servers[]` в роли + включённые тулы + `poll` на
нужных READ + seed, затем назначение роли сотруднику и Старт. Хост **не**
содержит строк `Drive`, `1c`, `PurchaseOrder`.

Порядок приёмки (Q-H-6): **сначала mock, потом Drive**. Живой Drive не
блокирует merge хоста и не входит в pytest CI. Роль «клерк метаданных» —
отдельная задача после хоста.

### 6.1 Этап mock (входит в DoD v1)

Автотесты и ручной прогон в конфигураторе против `transport: mock`:
создать сотрудника, старт, тики, очередь approval (карточка), стоп,
чекпоинт, повторный старт без seed. CI: `pytest -q -m "not slow"`.

### 6.2 Этап Drive (после зелёного mock, ручной чеклист)

Когда mock-хост работает — тот же сотрудник / роль `procurement` с уже
прописанным `drivemcp` http:

1. На READ-датчиках стоит `poll: true` (миграция YAML).
2. Старт против живого `hs/mcp` (публикация доступна локально).
3. В журнале — реальные READ, не четыре mock-склада лаборатории.
4. Стоп → чекпоинт → Старт без повторного seed.
5. WRITE `create_purchase_order` ждёт в **карточке**, пока человек не одобрит.

Пункт 6.2 не обязан быть зелёным, чтобы закрыть код хоста. Он обязан быть
пройден, прежде чем объявлять «сотрудник работает с базой».

## 7. Ограничения (обязательны)

| # | Ограничение |
|---|---|
| **H1** | GUI не конструирует `MCPCapability` / `SeedEpisode` в обход `role_config` / `compose_roles` |
| **H2** | Единственная точка WRITE — `ApprovalGate` |
| **H3** | HIGH_WRITE / IRREVERSIBLE нельзя сделать auto_execute |
| **H4** | `decision_only=True` на waking-тике; store эпизода — после известного исхода |
| **H5** | Старт с невалидной ролью или невалидным составом невозможен |
| **H6** | Недоступный live-транспорт на старте → `error`, не mock fallback |
| **H7** | Изменение `role_ids` только в `stopped`. YAML роли можно править всегда; running-сессия держит снимок Start |
| **H8** | Worker не трогает Tk; UI не блокируется на `call_tool` |
| **H9** | Хост не импортирует `nowa_sandbox` и не добавляет оси в `AffectiveSpace` |
| **H10** | Dry Run роли не запускает `EmployeeSession` |
| **H11** | Сон не чаще `sleep.min_interval_s` стенного времени; тик и сон — независимые поля |
| **H12** | Seed только при пустой памяти. Старт после Стоп не пересеивает гиппокамп |
| **H13** | Стоп без успешной записи `mind.pkl` не считается «нормальным stopped» без сообщения об ошибке сохранения |
| **H14** | Нет лимита на число сотрудников и на число одновременных `running` |
| **H15** | Одобрение: только карточка + счётчик `pending` в списке. Нет всплывающего уведомления / звука / модалки |
| **H16** | Хост опрашивает только `poll: true`. Галочка на каждом туле роли; WRITE не может быть poll |
| **H17** | CI и DoD v1 — mock. Живой Drive — следующий ручной шаг, не pytest |

## 8. Тесты (минимум)

Файл: `Demo/Virtual company/tests/test_employee_host.py` (+ controller).

- `compose_roles` одного id ≡ `load_role_config` этой роли.
- Две роли, один tool **name**, разные `server_id` → два органа, не ошибка.
- Две роли, один и тот же `tool_id`, эквивалентные capability → один орган.
- Тот же `tool_id`, разный `risk_level` → `RoleConfigError`.
- Два сервера с одним `server_id` и разным `url` → ошибка.
- `sensor_poller`: в poll set только `poll: true`; WRITE с `poll: true` не
  загружается; READ `poll: false` не зовётся, даже если required пуст.
- GUI Tools: чекбокс poll на READ; на WRITE disabled.
- Сессия mock: start → N tick → stop → `mind.pkl` существует → start →
  число эпизодов ≥ после первого stop, seed второй раз не добавляет дубликаты
  (или seeder не вызывался — явная проверка).
- Пустой сотрудник (нет mind): start при `seed_intuition: true` сидит корпус.
- `tick_interval_s=60` не превращает `sleep.min_interval_s=3600` в «спать
  каждые 60 тиков»; за окно короче часа при стабильном давлении сон 0 раз.
- `auto_execute=True` не проходит для HIGH_WRITE.
- Маршрутизация: `mcp__alpha__x` не зовёт транспорт `beta`.
- i18n EN/RU, `assert_string_parity`. Слова UI — «сотрудник», не «агент».

Живой Drive в CI не гонять. Чеклист §6.2 — после mock, не вместо него.

## 11. Принятые решения (все Q-H закрыты)

1. Несколько ролей = union органов. Ключ органа = `tool_id` (MCP + имя тула).
2. Concurrent сотрудники: без лимита, N потоков в процессе GUI.
3. Процесс v1: поток, не subprocess.
4. Память: полный чекпоинт на Stop, полное восстановление на Start.
5. Имя в UI: «Сотрудники»; файл: `employee.yaml`.
6. Приёмка: сначала mock (DoD / CI), потом ручной Drive (§6.2). Роль клерка
   метаданных — после хоста. (Q-H-6)
7. Тик настраивается **на сотрудника** (`tick_interval_s`: 1 с, 60 с, …).
8. Сон настраивается **на сотрудника** в стенных секундах, не «каждый тик».
9. `auto_execute` по умолчанию false.
10. ⚠ роли не блокирует назначение; ✗ блокирует.
11. Смешанный mock+http в составе — норма.
12. Seed только если память пуста.
13. `mcp_overrides` в v1 нет; разные базы на роль — этап B.
14. Редактор роли не блокируется running-сотрудником; нужен ручной рестарт,
    чтобы подхватить YAML.
15. Approval: только карточка + `pending: N` в списке. Нет всплывающего уведомления / звука /
    модалки. (Q-H-4)
16. Опрос сенсоров: явная галочка `poll` на каждом туле роли. Дефолт false.
    WRITE poll запрещён. `poll_defaults` — если у датчика есть required. (Q-H-9)
