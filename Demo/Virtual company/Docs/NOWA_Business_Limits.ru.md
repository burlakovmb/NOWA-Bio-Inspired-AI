# Слой тела — бизнес-лимиты, объявленные ролью

English: [NOWA_Business_Limits.en.md](NOWA_Business_Limits.en.md)

Модуль: `Demo/Virtual company/src/nowa_body/business_limits.py` (только stdlib), подключён в `BusinessAgentRuntime` сотрудника (`nowa_body/runtime.py`, подкласс runtime платформы).
Связано: [NOWA_Body_Lessons.ru.md](NOWA_Body_Lessons.ru.md) (урок «ждать» идёт через `teach`).

Ядро (`src/`, включая слой тела платформы `mcp_body`) не меняется.

---

## 1. Проблема

У роли бывают правила, которые вызов не должен нарушать никогда, например «не тратить больше, чем доступно». Если единственная защита — то, чему научился ум, защита не лучше обучения: агент, который научился действовать, будет действовать и при исчерпанной сумме, и последней защитой остаётся шлюз одобрения. Учить такое правило как интуицию — ещё и не тот уровень: правило не нужно открывать заново при каждой нехватке.

`hard_constraints` — архитектурные инварианты, их нельзя отключить конфигом. Бизнес-лимиты — другого рода: объявляются ролью в `config.yaml`, читаются из мира на каждом такте, исполняются телом.

## 2. Контракт

Роль перечисляет лимиты в `business_limits`:

```yaml
business_limits:
- name: quota                       # любое имя; возвращается хосту
  tools: [mcp__desk__reserve_slot]  # WRITE-инструменты под лимитом; пусто = все WRITE
  available: results.mcp__desk__get_quota.left      # путь в состоянии мира к остатку
  cost:                              # необязательно: цена вызова
    qty_param: count                 # привязанный параметр-количество
    unit_price: results.mcp__desk__get_prices.slots.{slot_id}.price  # подстановки {param}
  on_exceed: clip                    # clip | block (по умолчанию block)
  min_qty: 1                         # наименьшее количество, которое имеет смысл отправить после урезания
  lesson_reward: 0.6                 # >0: первый блок эпизода нехватки пишет урок «ждать»
  consequence: quota_kept            # имя последствия в этом уроке
```

Модуль знает только «сумму по пути в мире» и, по желанию, «параметр-количество × цену за единицу по пути в мире». Доменных имён полей в нём нет, все пути задаёт роль.

## 3. Проверка (`check_limit`, `apply_limits`)

Для привязанного вызова инструмента под лимитом — после `SchemaBinder` и до `ApprovalGate.route`:

| Ситуация | Вердикт | Причина |
| --- | --- | --- |
| Сумму не прочитать | blocked | `limit_unknown` |
| Сумма ≤ 0 | blocked | `nothing_left` |
| Вызов не оценить (нет количества, нет цены, цена ≤ 0) | ok | — (проверяется только «что-то осталось») |
| Стоимость ≤ суммы | ok | — |
| Стоимость > суммы, `on_exceed: clip`, `floor(сумма / цена) ≥ min_qty` | clipped (количество уменьшено) | `clipped_to_available` |
| Иначе | blocked | `over_available` |

Лимиты идут в порядке конфига; урезание видит следующий лимит; первый блок останавливает проверку. Параметры вызывающего не меняются. Строки без `available` пропускаются; неизвестный `on_exceed` означает `block`.

## 4. Runtime

`BusinessAgentRuntime(business_limits=..., limit_notifier=...)` принимает сырые строки конфига или разобранные лимиты.

- **Блок:** вызов не доходит до шлюза одобрения. В результате такта — `limit_blocked`, `limit_reason`, `limit_episode_start`, `waited: True`.
- **Урезание:** вызов идёт с уменьшенным количеством; в результате — `limit_clipped: [имена]`.
- **Эпизод нехватки.** Первый блок лимита открывает эпизод: один урок «ждать» (`teach(context, wait_and_monitor, lesson_reward, consequence)`), если `lesson_reward > 0`, и одно уведомление хосту (`limit_notifier({limit, reason, tool_id, params, available, cost, summary})`). Следующие блоки того же эпизода молчат. Эпизод закрывается, когда вызов проходит лимит или доступная сумма выросла выше суммы при первом блоке. Нечитаемый лимит (`limit_unknown`) эпизода не открывает. Ошибка уведомителя не ломает такт.

Урок идёт тем же путём, что и отзыв об одобрении ([NOWA_Body_Lessons.ru.md](NOWA_Body_Lessons.ru.md)): эпизод гиппокампа и лабильная метка; стабильные значения меняются только во сне.

Почему один урок на эпизод: урок на каждый заблокированный такт (десятки за одну нехватку) склоняет ум ждать во всех ситуациях, в том числе там, где правильно действовать (замер на закупщике Virtual company: проба на день 30 — 82 при уроке на каждый блок, 87 при одном на эпизод, 5 зёрен, ядро до #13).

## 5. Тесты

`Demo/Virtual company/tests/test_body_business_limits.py` (без домена: квота на бронирование): каждая строка §3, умолчания разбора, порядок лимитов, урезание видит следующий лимит; runtime — шлюз не достигается, один урок и одно уведомление на эпизод, подходящий вызов или выросшая сумма закрывают эпизод, нечитаемый лимит эпизода не открывает, падающий уведомитель, нулевая награда урока, отчёт об урезании.

Закупщик Virtual company объявляет так свой бюджет (`Demo/Virtual company/src/nowa_roles/procurement/config.yaml`; уведомления хоста становятся предупреждениями сотрудника) — тестируется в `test_business_limits.py`.

## 6. Вне объёма

- Лимиты на READ-инструменты; лимиты, которые не сводятся к «сумме и необязательной цене за единицу».
- Резервирование суммы между проверкой и учётом во внешней системе (следующее чтение обновляет мир).
