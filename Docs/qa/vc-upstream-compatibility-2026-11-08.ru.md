## Версия и объём изменений репозитория

Локальная ветка `vc/procurement-training` сохраняет прежнюю реализацию
в `4ef84a195b31474c47eabf821fb262da68b917fa`, затем merge
`cdc71eaa59cc4c895b09fd304421bbefc7885e85` объединяет её с upstream main
`039fd0ae857268de8fc40314e299eacbac6bae3d`. Merge прошёл без конфликтов.
Дерево `src/` после объединения точно совпадает с upstream
`0ca484475e9547fdab17a0c2b08638531500a25d`; корневые `tests/` также совпадают.
Самостоятельных изменений ядра и переписывания истории не было.

WIP-коммит содержит `25` явно отобранных файлов кода, синтетических тестов,
спецификаций и QA. Личные/сессионные материалы, корпусы/умы Компании,
результаты экспериментов и локальные настройки агентов/инструментов исключены.
До merge проверен частный резервный архив; неизменность исключённых локальных
файлов также проверена. Push и публикации не было. См.
[отчёт о срезе до синхронизации](vc-onboarding-snapshot-2026-11-08.ru.md).

  границы значений, неизменность stable наяву, захват во сне и save/load.
- Исходный полный корневой прогон явно прерван, код `1`, без итогового вердикта

- Доверенные архивные копии ума сотрудника и baseline роли загрузились на новом

  менеджера ведут на восстановленные объекты intent, labile и plasticity.
  Исходный ум и элементы архива неизменны. Эта проба не вызывала решений,
  уроков и сна и не сохраняла ум сотрудника.

Среда: корневая `.venv`, Python `3.14`, `NOWA_STRICT_LEARNING=1`,
`PYTHONDONTWRITEBYTECODE=1`, `PYTHONUTF8=1`, SDL dummy drivers, раздельные
временные каталоги. Отдельные демо Colony/Tamagotchi, живая ERP и внешняя LLM
в рабочем цикле не запускались. Программная совместимость не доказывает навык
закупок. Это интеграционная проверка координатора, а не новое независимое
финальное ревью всего поведения продукта.

## Влияние PR #63

| Изменение | Последствие для VC |
|---|---|
| Дробные рейтинги обратной связи сохраняются | API оценок наставника теперь сохраняет дроби. Существующий `store_lesson` уже передавал непрерывные награды через `_record_known_outcome`; объявлять все старые награды уроков округлёнными неправильно. |
| Alpha сна ограничена `0.25 * alpha_online` | Старое числовое `alpha_sleep_default=0.08` остаётся сохранённым, но даёт `0.0075` при `alpha_online=0.03`. Последующий сон работает по новому правилу. Простая загрузка checkpoint не воспроизводит прежнюю траекторию обучения. |
| Производная alpha сна остаётся `None` | Новые агенты следуют текущей online rate после применения генов factory. Старые числовые значения остаются явными потолками. Не заменять настройки ради получения прежней оценки. |
| Граница V следует `1/(1-gamma)` | При `gamma=0.95` граница примерно `20` вместо `1`. Это меняет дальнейшую динамику значений; VC не перемасштабирует награды и TD-error clip. |
| `alpha_sleep_ratio` сохраняется | Новые save/load должны его удерживать. Загрузку старых файлов без ключа проверяют тесты upstream. |

Хост VC не переопределяет эти скорости и границы value layer. Его явное
время и вход через `Agent.sleep` по-прежнему необходимы. PR #63 не исправляет
замену ссылок labile/plasticity в core-storage и не добавляет расширение intent
для VC, поэтому существующие адаптеры checkpoint остаются нужны. Загрузка
старых меток не является исправлением прошлого или разрешением продолжить работу.

PR #61 и PR #62 преимущественно меняют Colony/lifetime и обработку скрытых
сбоев, включая общие компоненты mortality/swarm. Они импортированы без правок;
полная квалификация их демо здесь не проводилась.

## Необходимая адаптация перед следующим обучением

Завершённые проверки VC и загрузки не указывают на необходимость дополнительных
изменений продуктового кода. Экспериментальная приёмка требует следующего:

1. Исправить P2 отдельного comparator: требовать полные уникальные ключи `567`
   старых / `216` новых строк и фиксированные метки; вычислять правильность и
   бюджетные счётчики по решениям, отклонять несогласованные сводки. Критерий
   не ослаблять.
2. Зафиксировать новый план с merge-коммитом/деревом ядра, согласованным корпусом,
   baseline, политикой частных RNG и согласованным модельным расписанием уроков.
   Результаты старого ядра и прерванные оценки сохранить как историю.
3. Повторно оценить неизменный основной ум и кандидата с одинаковой политикой
   решений нового ядра; проверить восстановление и последующий сон в новом
   процессе. Исторический baseline — явный выбор эксперимента, а не заново
   обученные предпосылки роли на новом ядре.
4. Отдельно квалифицировать учебную программу. Проход тестов или загрузка ума
   не восстанавливают Stage 1a/1b READY, не подтверждают бюджетную политику,
   не запускают живого сотрудника и не разрешают запись в ERP. Кандидат не
   принимается автоматически.

Новый учебный эксперимент, исправление comparator и профессиональная
квалификация в эту синхронизацию не входили.
